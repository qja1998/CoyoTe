## 1. 멤버별 프로필

### KWON — "Algorithm-First Explorer" (알고리즘 우선 탐험가)

| 항목 | 평가 |
|------|------|
| 제출 수 | 12개 (최다, 유일한 week 5 제출자) |
| 구조 성숙도 | 중하 |
| 알고리즘 성숙도 | **최상** |
| 가독성 | 중 |

**코드 스타일 특징:**
- 래퍼 패턴이 비일관적: `def solve()`, 플랫 스크립트, `PathFinder` 클래스 등 문제마다 다름
- 주석에 사고 진화 과정이 담김 ("누가 봐도 DP"). 이전 시도를 주석으로 보존
- 변수명: 간결하고 설명적 (`volumes`, `idx_to_pos`, `val_to_idx`)
- 유일한 클래스 사용자 (1520 `PathFinder` — 비공개 메서드 `_valid_path` 포함)

**알고리즘 접근:**
- 가장 넓은 알고리즘 레퍼토리: 비트마스크(x2), Edmonds-Karp, 백트래킹, deque 회전, 공간 최적화 DP
- 1495에서 BFS → DP → Set 기반으로 3가지 접근법 시도 — **메타인지적 접근**
- 비트마스크 활용이 자연스러움 (1194 키 관리, 2481 XOR)
- 1904에서 `prev1/prev2` 공간 최적화 DP — 실용적 효율성 인식

**강점:** 빠른 반복, 다양한 접근 시도, 그룹의 추진력
**약점:** 구조적 일관성 부족, 가끔 과도한 설계 (CP에서의 OOP)

### JAEFAN — "Methodical Decomposer" (체계적 분해자)

| 항목 | 평가 |
|------|------|
| 제출 수 | 8개 (week 1, 3 참여, week 2 불참) |
| 구조 성숙도 | **최상** |
| 알고리즘 성숙도 | 중상 |
| 가독성 | **최상** |

**코드 스타일 특징:**
- **가장 일관된 템플릿**: 항상 `def main()`, `inputf = sys.stdin.readline`, `DIRECTIONS` 상수, `if __name__` 가드
- 프로덕션 스타일 코딩: docstring, type hints (`List`, `Tuple`), 번호 매긴 단계별 주석
- 1194에서 "scratchpad" 섹션으로 사전 분석 후 코딩
- 함수 분리가 교과서적 (2638: `mark_outside_air` → `find_melting_cheese` → 메인 루프)

**알고리즘 접근:**
- 안정적이고 정확하지만 창의적이진 않음
- 1194에서 비트마스크 대신 문자열 키 관리 — 가독성 우선, 효율성 양보 (`normalize_keys()`의 O(k log k) 오버헤드)
- 문제 분해 능력이 뛰어남: 복잡한 문제를 명확한 단계로 나눔

**강점:** 경쟁 프로그래밍 실전에서도 통하는 템플릿 접근, 최고 수준의 문서화
**약점:** 비트마스크 활용 미숙, week 2 (그래프/유량) 불참이 약점 시사

### HOON — "Learning-in-Public" (공개 학습자)

| 항목 | 평가 |
|------|------|
| 제출 수 | 6개 (week 2, 3 참여, week 1 불참) |
| 구조 성숙도 | 중 |
| 알고리즘 성숙도 | 중하 |
| 가독성 | 하 (외부 독자 기준) / **상 (학습 자료 기준)** |

**코드 스타일 특징:**
- 일관된 `def main()` + `inputf` 사용
- **대화체 주석**: "아빠한테 회의랑 회의실을 물려받았다는게 뭘까...", "어려운데???"
- 이전 시도를 모두 보존: 주석 처리된 stack DFS, 빈 함수 스텁 (`def BFS(): pass`)
- 고정 크기 배열 (`dp = [0] * 10001`), ASCII 코드 기반 128 크기 배열

**알고리즘 접근:**
- 가장 투명한 성장 궤적: 1520에서 stack DFS → 재귀 DFS+DP 진화 과정이 완전히 기록됨
- 2481에서 덧셈/뺄셈 → XOR 비트 연산으로의 전환
- "이 발상이 도저히 안 떠올라서 선생님과 대화를 좀 했음" — 도움 요청을 숨기지 않음
- 19621에서 불필요한 정렬, 인덱싱 실수 등 구현 정확도 개선 필요

**강점:** 그룹의 심리적 안전 자산 — 어려움을 공유하여 모두가 편하게 질문할 수 있는 문화 조성
**약점:** 구현 정확도, 제출 수 적음, 저널링과 문서화의 구분 필요

### SEOYUN — "Creative Modularizer" (창의적 모듈화 전문가)

| 항목 | 평가 |
|------|------|
| 제출 수 | 9개 (week 1-3 꾸준 참여) |
| 구조 성숙도 | **최상** |
| 알고리즘 성숙도 | 상 |
| 가독성 | 상 |

**코드 스타일 특징:**
- 최고 수준의 모듈화: `make_graph()`, `bfs()`, `max_flow()` 등 작은 단위의 독립 함수들
- 깔끔하고 간결. 주석은 최소지만 충분
- `sys.stdin.readline` 미사용 — 잠재적 TLE 위험
- 이름 짓기에 일관성: `horse_map`, `bottle_neck`, `contact_side`

**알고리즘 접근:**
- **가장 독립적인 사고**: 다른 멤버들과 다른 접근법을 자주 선택
  - 1495: 다른 멤버들이 set DP일 때 **BFS** 사용
  - 1520: 다른 멤버들이 DFS+메모일 때 **heapq 기반 DP** (전체 데이터셋에서 가장 창의적 솔루션)
  - 2481: 비트 연산 대신 **문자열 조작** 방식
- 19621에서 2D DP `dp[i][0/1]` (선택/미선택) — 다른 멤버들의 1D DP와 다른 정식화
- 모듈 구조가 알고리즘 실험을 가능하게 함: 교체 가능한 단위로 비표준 접근 시도

**강점:** 독립적 사고, 모듈화, 가장 균형 잡힌 코더
**약점:** `sys.stdin.readline` 미사용, 사고 과정이 코드에 드러나지 않아 동료 학습 전이가 약함

## 2. 교차 분석 매트릭스

### 구조 vs 알고리즘 성숙도

| 멤버 | 구조적 성숙도 | 알고리즘 성숙도 | 관계 |
|------|------------|--------------|------|
| **SEOYUN** | 상 | 상 | 구조가 알고리즘을 **지원** |
| **JAEFAN** | 상 | 중 | 구조가 알고리즘을 **대체** |
| **KWON** | 중하 | 상 | 알고리즘이 구조를 **앞지름** |
| **HOON** | 중 | 중하 | 구조가 학습 상태를 **반영** |

### 알고리즘 정교함 vs 가독성 (역상관)

```
알고리즘 순위:  KWON > SEOYUN > JAEFAN ≈ HOON
가독성 순위:    SEOYUN > JAEFAN > KWON > HOON
```

핵심 인사이트: 어려운 솔루션일수록 설명이 더 필요한데, 가장 정교한 풀이를 작성하는 사람이 가장 적게 설명하는 경향이 있음.

### 실전 CP 효율성 순위

1. **KWON** — 가장 많은 산출물, 알고리즘적으로 건전한 선택
2. **SEOYUN** — 가장 균형적. `sys.stdin.readline`만 추가하면 1위
3. **JAEFAN** — 템플릿 규율이 유용하지만 알고리즘 효율성 양보가 있음
4. **HOON** — 정직함의 교육적 가치는 높지만 구현 정확도가 가장 시급한 과제

### 1520 (내리막길) — 최고의 단일 문제 진단

같은 문제에 대한 4가지 다른 접근법이 각 멤버의 특성을 가장 잘 드러냄:
- **KWON**: 클래스 기반 DFS + 메모이제이션 (`PathFinder`)
- **JAEFAN**: 중첩 함수 DFS + 메모이제이션 (docstring 포함)
- **HOON**: stack DFS 실패 → 재귀 DFS+DP 성공 (전 과정 기록)
- **SEOYUN**: **heapq 기반 DP** (Dijkstra 스위프) — 전체 데이터셋에서 가장 창의적 해법

1. **"과정 vs 결과물" 이중 트랙**: PR에서는 사고 과정을, 최종 커밋에서는 정리된 코드를 각각 보여주는 문화 권장
